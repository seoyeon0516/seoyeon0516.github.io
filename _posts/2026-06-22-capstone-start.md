## [캡스톤디자인] Flutter로 AI 헬스케어 서비스 MVP 화면 설계하기: On-Care 프론트엔드 구현 기록

캡스톤디자인 프로젝트를 진행하면서 가장 많이 고민한 부분은 “어떤 기술을 사용할 것인가”보다 “사용자가 이 서비스를 실제로 이해하고 사용할 수 있을까”였다. 아이디어 단계에서는 기능을 많이 넣는 것이 쉬워 보인다. 식단 기록, 운동 관리, 건강 지표 추적, AI 코칭, 헬스장 탐색, 알림 기능까지 모두 넣으면 완성도 높은 헬스케어 서비스처럼 보인다. 하지만 막상 앱 화면으로 구현하려고 하면 문제가 달라진다.

기능이 많을수록 사용자는 어디서 무엇을 해야 하는지 헷갈릴 수 있다. 특히 건강관리 서비스는 사용자가 매일 반복해서 들어오는 앱이기 때문에, 첫 화면에서 현재 상태를 빠르게 파악하고, 필요한 기록을 부담 없이 입력하고, 그 결과가 다시 피드백으로 이어지는 흐름이 중요하다.

이번 글에서는 캡스톤디자인 프로젝트 **On-Care**의 Flutter 프론트엔드 MVP를 구현하면서 고민했던 화면 구조, 사용자 흐름, 디자인 시스템, 그리고 MVP 단계에서 API 연동보다 사용자 경험 검증을 먼저 선택한 이유를 정리한다.

---

## 프로젝트 소개: On-Care

On-Care는 불규칙한 생활 속에서 고혈압·당뇨 위험을 관리해야 하는 20~30대를 위한 AI 건강 코칭 통합 헬스케어 플랫폼이다. 서비스의 핵심 방향은 단순한 기록 앱이 아니라, 식단·운동·건강 지표를 한곳에서 확인하고 사용자의 누적 기록을 바탕으로 맞춤형 피드백을 제공하는 것이다.

프로젝트에서 기획한 주요 기능은 다음과 같다.

| 기능 | 설명 |
| --- | --- |
| 홈 대시보드 | 오늘의 건강 상태, 식단 요약, 운동 기록, 일정, AI 피드백을 한 화면에서 확인 |
| 식단 기록 | 끼니별 음식 기록과 칼로리, 나트륨, 당류 등 주요 영양 정보 확인 |
| 운동 관리 | 주간 운동 기록, 운동 시간, 소모 칼로리, 연속 기록 확인 |
| My Health | 체중, 혈압, 혈당 등 건강 지표 입력 및 추이 확인 |
| AI 코치 | 사용자의 건강 기록을 바탕으로 코칭을 받는 대화형 화면 |
| 헬스장 찾기 | 주변 운동 시설과 트레이너 연계 흐름을 고려한 O2O 화면 |
| 알림 | 기록 유도, 건강 일정, 피드백 확인을 위한 알림 화면 |

최종 서비스 관점에서는 AI 식단 분석, RAG 기반 코칭, 실제 위치 기반 API, 백엔드 서버 연동이 필요하다. 다만 이번 캡스톤 MVP 단계에서는 Flutter 기반 프론트엔드 화면과 사용자 흐름을 우선적으로 구현했다.

---

## 왜 Flutter를 선택했나

헬스케어 앱은 모바일 중심 서비스이지만, 캡스톤디자인 프로젝트에서는 발표, 시연, 피드백 수집까지 고려해야 한다. 모바일 앱만 만들면 실제 기기 설치가 필요하고, 웹만 만들면 향후 앱 서비스로 확장할 때 다시 구현해야 하는 부담이 생긴다.

Flutter는 하나의 코드베이스로 Android, iOS, Web을 함께 고려할 수 있다는 점에서 MVP 구현에 적합했다. 특히 On-Care처럼 건강 기록 카드, 차트, 캘린더, 하단 탭, 대시보드 등 화면 요소가 많은 서비스에서는 UI 일관성을 유지하는 것이 중요했다.

또한 Flutter는 위젯 단위로 화면을 구성하기 때문에 반복되는 UI를 컴포넌트화하기 좋다. 캡스톤 프로젝트처럼 여러 명이 동시에 작업하는 환경에서는 공통 버튼, 카드, 차트, 입력 컴포넌트를 정리해두는 것만으로도 화면 간 완성도 차이를 줄일 수 있다.

---

## MVP의 핵심은 “기능 목록”이 아니라 “사용자 흐름”이었다

처음에는 기능별 화면을 각각 구현하는 방식으로 접근하기 쉽다. 예를 들어 식단 화면, 운동 화면, 건강 화면, AI 코치 화면을 따로 만들고 각 화면 안에 필요한 UI를 배치하는 식이다.

하지만 헬스케어 앱에서 중요한 것은 개별 화면의 존재보다 화면 사이의 연결이다. 사용자는 단순히 “식단 화면이 있다”는 이유로 앱을 계속 쓰지 않는다. 사용자가 앱을 열었을 때 현재 자신의 상태를 이해하고, 기록을 입력하고, 그 기록이 다시 피드백으로 이어지는 경험이 있어야 한다.

그래서 On-Care의 프론트엔드 MVP는 다음과 같은 흐름을 기준으로 설계했다.

```text
앱 진입
  ↓
홈 대시보드에서 오늘의 건강 상태 확인
  ↓
식단 / 운동 / 건강 지표 중 필요한 기록 입력
  ↓
입력한 기록이 요약 카드와 추이 화면에 반영되는 구조로 설계
  ↓
AI 코치 화면에서 건강관리 피드백을 확인하는 흐름 제시
  ↓
필요한 경우 헬스장 찾기 / 일정 / 알림으로 연결
```

이 흐름을 먼저 잡아두니 각 화면의 역할도 더 명확해졌다. 홈 화면은 모든 기능을 나열하는 곳이 아니라 사용자의 오늘 상태를 요약하는 허브가 되었고, 식단과 운동 화면은 기록을 입력하는 도구가 되었으며, AI 코치 화면은 단순 챗봇 화면이 아니라 사용자의 기록을 바탕으로 조언을 받는 경험을 보여주는 화면이 되었다.

## 화면 구조를 기능 단위로 나눈 이유

프로젝트 규모가 커질수록 파일 구조는 생각보다 중요하다. 초반에는 `screens`, `widgets`, `models`처럼 단순하게 나누어도 충분해 보인다. 하지만 기능이 늘어나면 어떤 위젯이 어느 화면에 필요한지, 어떤 모델이 어떤 기능에 속하는지 헷갈리기 시작한다.

On-Care는 기능별로 화면을 확장해야 했기 때문에 `features` 중심 구조가 더 적합했다.

```text
lib/
├─ app/                 # 앱 진입, 라우팅, 전체 구조
├─ core/                # 공통 설정, 네트워크, 에러 처리 등
├─ design_system/       # 공통 UI 토큰, 버튼, 카드, 차트, 반응형 요소
├─ shared/              # 여러 기능에서 함께 쓰는 공통 요소
└─ features/
   ├─ dashboard/        # 홈 대시보드
   ├─ diet/             # 식단 기록
   ├─ exercise/         # 운동 관리
   ├─ my_health/        # 건강 지표 관리
   ├─ ai_coach/         # AI 코치 화면
   ├─ notification/     # 알림
   ├─ place/            # 헬스장 찾기
   ├─ schedule/         # 일정
   └─ vitals/           # 혈압, 혈당, 체중 등 지표
```

이 구조의 장점은 기능별 책임이 분명해진다는 점이다. 예를 들어 식단 화면을 수정할 때는 `features/diet`를 중심으로 보면 되고, 운동 화면을 수정할 때는 `features/exercise`를 중심으로 보면 된다. 공통으로 쓰는 버튼, 카드, 색상, 차트는 `design_system`에서 관리하므로 화면마다 스타일이 제각각 달라지는 문제도 줄일 수 있다.

캡스톤 프로젝트는 개발 기간이 길지 않기 때문에 “일단 돌아가게 만들기”가 중요하다. 하지만 동시에 팀 프로젝트이기 때문에 “나중에 다른 팀원이 봐도 이해할 수 있는 구조”도 중요하다. 기능 중심 구조는 이 두 가지 요구를 어느 정도 동시에 만족시켜 주었다.

## 디자인 시스템을 먼저 정리한 이유

헬스케어 앱은 많은 정보를 한 화면에 담아야 한다. 칼로리, 나트륨, 당류, 혈압, 혈당, 체중, 운동 시간, 소모 칼로리처럼 숫자 정보가 많고, 사용자에게 위험 신호나 개선 방향을 보여주어야 한다. 이때 화면마다 카드 스타일이나 색상 기준이 다르면 앱 전체가 산만해 보인다.

그래서 On-Care에서는 공통 UI를 디자인 시스템처럼 정리하는 방향을 잡았다.

```text
design_system/
├─ tokens/      # 색상, 간격, radius, typography 등 기본 규칙
├─ atoms/       # 버튼, 아이콘, 텍스트 등 작은 단위 컴포넌트
├─ molecules/   # 카드, 입력 영역, 요약 박스 등 조합 컴포넌트
├─ charts/      # 건강 지표와 운동 기록을 보여주는 차트
├─ responsive/  # 화면 크기에 따른 레이아웃 대응
└─ theme/       # 앱 전체 테마
```

특히 건강관리 서비스에서는 색상을 신중하게 써야 한다. 예를 들어 빨간색은 위험, 초록색은 정상처럼 직관적으로 받아들여질 수 있지만, 너무 강한 색을 자주 사용하면 사용자가 불안감을 느낄 수 있다. 그래서 경고를 보여줄 때도 단순히 자극적인 색을 쓰기보다, 텍스트 설명과 함께 현재 상태를 이해할 수 있도록 구성하는 것이 중요했다.

또한 숫자만 나열하는 화면은 사용자가 의미를 파악하기 어렵다. 예를 들어 “나트륨 2,100mg”이라는 숫자만 보여주는 것보다, 오늘 목표 대비 어느 정도인지, 어떤 식사에서 많이 섭취했는지, 다음 식사에서 무엇을 조절하면 좋은지까지 이어지는 화면이 더 실용적이다.

이번 MVP에서는 모든 분석 로직을 완성하기보다, 이런 정보가 들어갈 수 있는 화면 구조를 먼저 설계하는 데 집중했다.

## 홈 대시보드: 모든 기능의 입구 만들기

홈 대시보드는 On-Care에서 가장 중요한 화면이다. 사용자가 앱에 들어왔을 때 처음 보는 화면이기 때문이다. 여기서 사용자는 오늘 자신의 상태를 빠르게 파악하고, 필요한 행동으로 이동할 수 있어야 한다.

대시보드에는 다음과 같은 요소를 배치하는 방향으로 설계했다.

- 오늘의 식단 요약
- 나트륨·당류 등 주요 영양 지표
- 오늘 또는 이번 주 운동 기록
- 체중·혈압·혈당 등 건강 지표
- AI 코치의 짧은 피드백
- 일정 및 알림으로 이동하는 진입점

여기서 중요한 것은 정보를 많이 넣는 것이 아니라 우선순위를 정하는 것이다. 홈 화면에 모든 데이터를 같은 비중으로 배치하면 사용자는 무엇을 봐야 할지 모른다. 따라서 “오늘 바로 확인해야 하는 정보”와 “자세히 보고 싶을 때 이동할 정보”를 구분했다.

예를 들어 식단 정보는 홈에서 간단한 요약만 보여주고, 자세한 끼니별 기록은 식단 화면으로 이동해 확인하도록 구성할 수 있다. 운동도 홈에서는 주간 누적이나 오늘의 운동 여부를 보여주고, 자세한 기록은 운동 화면에서 관리하도록 나누었다.

이런 구조는 앱을 처음 사용하는 사람에게도 기능을 자연스럽게 안내하는 역할을 한다.

## 식단 기록 화면: 입력 부담을 줄이는 것이 핵심이었다

식단 기록 기능은 헬스케어 앱에서 자주 등장하지만, 실제 사용자는 매 끼니마다 긴 입력을 반복하는 것을 부담스러워한다. 특히 On-Care의 주요 사용자는 바쁜 20~30대이기 때문에, 기록 과정이 복잡하면 서비스의 핵심 가치가 약해진다.

최종적으로는 음식 사진 기반 식단 인식과 영양 분석을 목표로 하지만, MVP 단계에서는 사용자가 식단을 기록하고 결과를 확인하는 화면 흐름을 먼저 구현하는 데 집중했다.

식단 화면에서 고려한 점은 다음과 같다.

1. 아침, 점심, 저녁, 간식처럼 사용자가 익숙한 단위로 기록을 나눈다.
2. 칼로리뿐 아니라 고혈압·당뇨 위험군에게 중요한 나트륨, 당류 정보를 함께 보여준다.
3. 기록 결과가 홈 대시보드와 연결될 수 있도록 요약 가능한 형태로 설계한다.
4. 사용자가 “무엇을 입력해야 하는지” 바로 알 수 있도록 버튼과 빈 상태 화면을 명확히 만든다.

기술적으로 복잡한 AI 분석보다 먼저 검증해야 했던 것은 사용자가 식단 기록 화면을 보았을 때 “아, 여기에 오늘 먹은 것을 기록하면 되는구나”라고 이해하는지였다. MVP에서는 이처럼 서비스의 기본 사용성을 먼저 확인하는 것이 중요했다.

## 운동 관리 화면: 성과보다 지속성을 보여주기

운동 화면은 단순히 운동 종류와 시간을 입력하는 화면으로 끝나면 아쉽다. 건강관리 서비스에서 운동 기록은 사용자의 행동 변화를 유도하는 역할을 해야 한다.

그래서 운동 화면에서는 “이번 주 얼마나 운동했는지”, “연속 기록이 이어지고 있는지”, “운동 시간이 어떻게 쌓이고 있는지”를 보여주는 방향을 고려했다. 사용자가 매일 완벽한 운동을 하지 않더라도, 작은 기록이 누적되고 있다는 느낌을 주는 것이 중요했다.

운동 화면에서 특히 신경 쓴 부분은 차트와 카드 구성이다. 텍스트만으로 운동 기록을 보여주면 사용자는 변화량을 직관적으로 파악하기 어렵다. 반면 주간 기록을 시각적으로 보여주면 사용자는 자신의 패턴을 더 쉽게 이해할 수 있다.

MVP 단계에서는 실제 운동 데이터 연동보다, 사용자가 운동 기록을 확인하고 다음 행동으로 이어갈 수 있는 화면 구조를 먼저 구현했다.

## My Health 화면: 건강 지표를 부담스럽지 않게 보여주기

혈압, 혈당, 체중 같은 건강 지표는 민감한 정보다. 단순히 수치를 보여주는 것만으로는 부족하고, 사용자가 자신의 상태를 이해할 수 있도록 도와야 한다.

My Health 화면에서는 다음과 같은 정보를 중심으로 구성했다.

- 체중 변화
- 혈압 기록
- 혈당 기록
- 최근 추이
- 건강 위험 신호 또는 안내 문구
- 활동 포인트 또는 기록 동기부여 요소

여기서 중요한 것은 “의학적 판단”을 앱이 직접 내려서는 안 된다는 점이다. 캡스톤 프로젝트의 MVP 단계에서는 의료적 진단을 제공하는 것이 아니라, 사용자가 자신의 기록을 확인하고 생활습관을 점검할 수 있도록 돕는 화면을 만드는 데 집중했다.

따라서 문구도 단정적인 진단보다 “최근 기록 기준으로 확인이 필요합니다”, “오늘은 나트륨 섭취를 조금 줄여보세요”처럼 행동을 유도하는 톤이 적합하다고 보았다.

---

## AI 코치 화면: 기술보다 기대 경험을 먼저 설계하기

On-Care의 중요한 차별점 중 하나는 AI 코칭이다. 하지만 AI 기능은 단순히 채팅창을 하나 붙인다고 완성되는 것이 아니다. 사용자는 AI가 왜 이런 말을 하는지, 어떤 데이터를 기준으로 조언하는지, 이 조언을 어디까지 신뢰해도 되는지 이해할 수 있어야 한다.

그래서 MVP 단계에서는 AI 엔진 자체보다 AI 코치 화면의 역할을 먼저 설계했다. AI 코치 화면은 다음과 같은 경험을 보여주어야 했다.

```text
사용자 기록 확인
  ↓
오늘의 건강 상태 요약
  ↓
식단·운동·건강 지표를 바탕으로 한 피드백 제시
  ↓
사용자가 추가 질문을 할 수 있는 대화형 흐름 제공
```

이때 중요한 것은 AI가 모든 것을 해결해주는 것처럼 보이지 않게 하는 것이다. 헬스케어 서비스에서 AI는 사용자의 판단을 대신하기보다, 사용자가 자신의 생활 패턴을 더 잘 이해하도록 돕는 보조자에 가까워야 한다.

따라서 AI 코치 UI는 친근하지만 과도하게 확신하지 않는 톤을 목표로 했다. 예를 들어 “당신은 위험합니다”가 아니라 “최근 기록을 보면 나트륨 섭취가 높은 편이에요. 오늘 저녁은 국물 섭취를 줄이는 방식으로 조절해볼 수 있어요”처럼 구체적이고 실천 가능한 피드백이 더 적합하다.

---

## API 연동보다 사용자 흐름 검증을 먼저 선택한 이유

On-Care는 최종적으로 식단 인식, 건강 데이터 기록, AI 코칭 기능이 서로 연결되는 헬스케어 플랫폼을 목표로 한다. 따라서 실제 서비스 단계에서는 백엔드 API와 AI 모델 연동이 반드시 필요하다.

다만 이번 캡스톤디자인 MVP 단계에서는 제한된 개발 기간 안에 서비스의 핵심 가치를 먼저 검증하는 것이 중요했다. 특히 사용자가 앱에 진입해 오늘의 건강 상태를 확인하고, 식단·운동·건강 기록을 입력하며, AI 코칭 화면에서 피드백을 받는 전체 흐름이 자연스럽게 이어지는지를 확인하는 것이 우선이었다.

그래서 이번 구현에서는 실제 API 연동을 완성도 낮게 급하게 포함하기보다, Flutter 기반 프론트엔드 화면과 mock 데이터를 활용해 주요 사용자 시나리오를 먼저 완성하는 방향을 선택했다. 이를 통해 백엔드가 완성되기 전에도 서비스의 정보 구조, 화면 전환, 기록 입력 방식, 대시보드 구성, AI 코칭 UI의 적절성을 검토할 수 있었다.

즉, 이번 MVP의 목적은 완성된 운영 서비스 구현이 아니라, On-Care가 제공하려는 건강관리 경험이 사용자에게 이해 가능한 흐름으로 전달되는지 검증하는 것이었다. 이후 단계에서는 현재 구현된 프론트엔드 구조를 기반으로 실제 건강 데이터 저장 API, 식단 분석 API, AI 코칭 API를 순차적으로 연결할 수 있도록 확장할 계획이다.

## mock 데이터를 사용할 때 주의한 점

mock 데이터는 대충 넣으면 화면을 채우는 용도로만 끝난다. 하지만 잘 설계된 mock 데이터는 실제 서비스 흐름을 미리 검증하는 도구가 될 수 있다.

On-Care에서는 mock 데이터를 사용할 때 다음 기준을 고려했다.

| 기준 | 설명 |
| --- | --- |
| 실제 사용자 시나리오와 맞는가 | 임의 숫자가 아니라 건강관리 맥락에서 자연스러운 값인지 확인 |
| 여러 화면에서 재사용 가능한가 | 홈, 식단, 운동, 건강 화면이 서로 다른 이야기를 하지 않도록 구성 |
| 향후 API 응답으로 바꾸기 쉬운가 | 화면에 하드코딩하기보다 model 형태로 분리 가능한 구조 고려 |
| 빈 상태를 표현할 수 있는가 | 기록이 없을 때 사용자가 무엇을 해야 하는지 안내 |

예를 들어 건강관리 앱에서는 “오늘 기록이 없는 상태”도 중요하다. 실제 사용자는 매일 모든 기록을 입력하지 않는다. 따라서 데이터가 있을 때의 화면뿐 아니라, 데이터가 없을 때 어떤 안내 문구와 버튼을 보여줄지도 함께 고려해야 한다.

## 프론트엔드 MVP를 만들면서 배운 점

### 1. 화면 구현 전에 사용자 흐름을 먼저 정해야 한다

기능별 화면을 먼저 만들면 앱이 단절되어 보일 수 있다. 반대로 사용자가 어떤 순서로 앱을 사용할지 먼저 정하면 각 화면의 역할이 분명해진다. On-Care에서는 홈 대시보드를 중심으로 식단, 운동, 건강, AI 코치 화면이 연결되도록 설계한 것이 전체 구조를 잡는 데 도움이 되었다.

### 2. 공통 컴포넌트를 정리하면 후반 수정이 쉬워진다

캡스톤 프로젝트 후반에는 예상보다 수정할 일이 많다. 발표 자료에 맞춰 화면 문구를 바꾸거나, 시연 흐름에 맞춰 버튼 위치를 조정하거나, 디자인 톤을 통일해야 하는 상황이 생긴다. 이때 공통 버튼, 카드, 차트, 간격 규칙이 정리되어 있으면 수정 범위가 줄어든다.

### 3. mock 데이터도 설계가 필요하다

mock 데이터는 “임시 데이터”지만, 사용성 검증 단계에서는 실제 데이터처럼 보인다. 숫자가 너무 비현실적이거나 화면마다 데이터 맥락이 다르면 서비스 신뢰도가 떨어진다. 특히 헬스케어 서비스에서는 수치 정보가 많기 때문에 mock 데이터도 자연스럽게 구성해야 한다.

### 4. MVP에서는 구현 범위를 명확히 말하는 것이 중요하다

캡스톤 프로젝트에서는 하고 싶은 기능이 많아질수록 구현 범위가 흐려질 수 있다. 하지만 실제로 구현한 것과 설계 단계인 것을 구분해서 설명하는 것이 오히려 프로젝트의 신뢰도를 높인다. On-Care에서도 Flutter 프론트엔드 MVP에서 구현한 화면과, 이후 API 및 AI 연동으로 확장할 부분을 구분하는 것이 중요했다.

## 비슷한 프로젝트를 진행한다면 추천하는 체크리스트

AI 헬스케어 앱이나 건강관리 앱의 프론트엔드 MVP를 만든다면 다음 순서로 접근하는 것을 추천한다.

1. 기능 목록보다 사용자 흐름을 먼저 정리한다.
2. 홈 화면이 어떤 정보를 요약해야 하는지 먼저 결정한다.
3. 기록 기능은 입력 부담을 줄이는 방향으로 설계한다.
4. 건강 수치는 숫자만 보여주지 말고 의미를 함께 전달한다.
5. AI 기능은 실제 엔진 구현 전에도 사용자가 기대하는 경험을 화면으로 설계한다.
6. mock 데이터는 실제 시나리오처럼 자연스럽게 구성한다.
7. 공통 컴포넌트와 디자인 토큰을 정리해 화면 간 일관성을 유지한다.
8. API 연동이 늦어지더라도, 이후 연결 가능한 구조를 염두에 두고 model과 화면을 분리한다.
9. 구현된 기능과 설계 단계 기능을 명확히 구분해 설명한다.

## 마무리

On-Care 캡스톤디자인 프로젝트는 단순히 Flutter 화면을 여러 개 만드는 작업이 아니라, AI 헬스케어 서비스가 사용자에게 어떤 흐름으로 전달되어야 하는지 고민하는 과정이었다.

이번 MVP 단계에서는 API와 AI 엔진을 완성하는 것보다, 사용자가 앱에 들어와 자신의 건강 상태를 확인하고, 식단·운동·건강 기록을 관리하고, AI 코칭을 받을 수 있다는 전체 경험을 화면으로 설계하는 데 집중했다.

프론트엔드 MVP는 최종 서비스가 아니다. 하지만 잘 만든 MVP는 팀이 어떤 서비스를 만들고 있는지, 사용자가 어떤 가치를 느낄 수 있는지, 이후 어떤 기술을 연결해야 하는지를 분명하게 보여준다. 그런 점에서 On-Care의 Flutter MVP 구현은 프로젝트의 방향성을 구체화하는 중요한 단계였다.

> 본 기술블로그는 캡스톤디자인 프로젝트 **On-Care**의 Flutter 프론트엔드 MVP 구현 과정을 바탕으로 작성했습니다. On-Care는 20~30대 고혈압·당뇨 위험군을 위한 AI 건강 코칭 통합 헬스케어 플랫폼으로, 이번 글에서는 실제 서비스 구현 과정에서 사용자 흐름을 어떻게 화면으로 설계했는지, 식단·운동·건강 기록·AI 코칭·주변 장소 탐색 기능을 어떤 구조로 프론트엔드에 반영했는지를 정리했습니다. 또한 MVP 단계에서 API 연동보다 핵심 사용자 경험 검증을 우선한 이유와 향후 API 및 AI 기능 확장 방향도 함께 다루었습니다.
